# Migration Guide: v10 → v11

What changes when you upgrade from v10 to v11, and what to do about it.

## Breaking Changes

### Which app build is used

The service now finds Electron Builder apps built for Windows ARM64 and ia32 (`win-arm64-unpacked`, `win-ia32-unpacked`). It also follows Electron Builder's `defaultArch`: with `win.defaultArch: 'arm64'`, it finds the x64 build in `win-x64-unpacked`.

When your output directory holds builds for more than one architecture, the service now launches the one built for the machine running the tests, so your tests may launch a different app:

| Machine running the tests | Builds in the output directory            | v10 launched                        | v11 launches         |
| ------------------------- | ----------------------------------------- | ----------------------------------- | -------------------- |
| Windows ARM64             | `win-unpacked`, `win-arm64-unpacked`      | `win-unpacked`                      | `win-arm64-unpacked` |
| Linux x64                 | `linux-unpacked`, `linux-arm64-unpacked`  | `linux-arm64-unpacked`              | `linux-unpacked`     |
| Linux x64                 | `linux-unpacked`, `linux-armv7l-unpacked` | `linux-armv7l-unpacked`             | `linux-unpacked`     |
| Intel Mac                 | `mac`, `mac-arm64`                        | `mac-arm64`                         | `mac`                |
| Intel Mac                 | `mac`, `mac-universal`                    | `mac-universal`                     | `mac`                |
| Intel Mac                 | `mac-arm64`, `mac-universal`              | `mac-arm64`                         | `mac-universal`      |
| Apple Silicon Mac         | Forge `darwin-x64`, `darwin-arm64`        | `darwin-x64`                        | `darwin-arm64`       |
| Linux ARM64               | Forge `linux-x64`, `linux-arm64`          | `linux-x64`                         | `linux-arm64`        |
| Windows ARM64             | Forge `win32-x64`, `win32-arm64`          | `win32-x64`                         | `win32-arm64`        |
| Windows x64               | Forge `win32-ia32`, `win32-x64`           | `win32-ia32` (Electron 43 or older) | `win32-x64`          |

A machine running an x64 Node.js counts as x64, including an Apple Silicon Mac under Rosetta and a Windows ARM64 machine under emulation.

v11 also finds Electron Forge builds that v10 missed. v10 looked only for x64 builds when `browserVersion` held a Chromium version or the Electron version was unknown, and from Electron 44 it skipped `win32-ia32` and `linux-armv7l`.

To keep launching a specific build, set [`appBinaryPath`](../configuration.md#appbinarypath). See [Which build is used](../configuration.md#which-build-is-used) for the full order.

### `getBinaryPath()` takes no Electron version

Call it as `getBinaryPath(packageJsonPath, appBuildInfo)`.

### API mock implementations run only in the app

An API mock's implementation, such as one set on `browser.electron.mock('app', 'getName')`, also ran in your test process each time the mock synced its calls. It now runs only in the app, and the mock copies its results from there.

A test can no longer count calls through a variable that the implementation updates. Assert on the mock's calls instead:

```ts
// v10
let callsCount = 0;
await mockGetName.mockImplementation(() => {
  if (typeof callsCount !== 'undefined') {
    callsCount++;
  }
  return 'mocked value';
});
expect(callsCount).toBe(1);

// v11
await mockGetName.mockImplementation(() => 'mocked value');
expect(mockGetName).toHaveBeenCalledTimes(1);
```

An error from the implementation is thrown in the app, where the caller can catch it, and no longer rejects the test's next `browser.electron.execute()`.

### The multiremote root's `execute()` resolves with one result per instance

On the multiremote root, `browser.electron.execute()` runs the script in every instance and resolves with their results, in instance order. It already did at runtime, but v10 typed it as resolving with one value, so code that read it as one value type-checked. v11 types it as an array.

Index or iterate the root's result, or call `execute()` on one instance:

```ts
const [nameA, nameB] = await multiRemoteBrowser.electron.execute((electron) => electron.app.getName());
const name = await multiRemoteBrowser.getInstance('app1').electron.execute((electron) => electron.app.getName());
```

`ElectronServiceAPI` takes a `ServiceApiTarget` parameter, `'instance'` by default, so `ElectronServiceAPI<'root'>` is the root's API.

### The multiremote root names each instance that failed

When an instance fails, the root's `browser.electron.execute()` and `browser.electron.emitEvent()` now wait for the others, then reject with an error naming each instance that failed, e.g. `execute failed on app2: …`. v10 rejected as soon as one failed, with that instance's error.

A test that matches the instance's message still passes, as the new message contains it. A test that checks the error's class or reads its properties now gets an `Error` with the instance's error as its `cause`, or an `AggregateError` of each instance's error when several failed.
