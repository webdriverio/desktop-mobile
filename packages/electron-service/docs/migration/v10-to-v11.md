# Migration Guide: v10 → v11

What changes when you upgrade from v10 to v11, and what to do about it.

## What's New in v11

v11 supports WebdriverIO v9 and v10. For the full list of changes, including the warning for an app build the machine can't run and the `connectionRetryTimeout` option for standalone sessions, see the [v11.0.0 release notes](../release-notes/v11.0.0.md). New features are additive and need no migration action.

## Breaking Changes

### Requirements

#### WebdriverIO v9 and v10

v11 supports WebdriverIO 9.33.0+ and 10.2.0+ (`^9.33.0 || ^10.2.0`), the first releases with the Node.js floors below. Update `webdriverio` and the `@wdio/*` packages to one of them.

If you move to WebdriverIO v10, follow the upstream [v9 → v10 migration guide](https://webdriver.io/docs/v10-migration) for the changes in your own tests, such as strict `$`, `multiremotebrowser`, `executeAsync` and Mocha 12.

#### Node.js

v11 needs Node.js 22 (22.23.4+), 24 (24.22.1+) or 26 (26.12.1+). Node.js 23.x and 25.x aren't supported. Older versions trust the compromised eMudhra intermediate CAs.

#### Optional peer dependencies

`webdriverio`, `@wdio/globals` and `@wdio/types` are now optional peers. They need WebdriverIO 9.33.0+ or 10.2.0+.

- **Testrunner mode:** nothing new to install. `@wdio/cli` and `@wdio/local-runner` provide all of them, and the service uses those copies.
- **Standalone mode** (no testrunner): install `webdriverio` and `@wdio/globals` next to the service, as the service's entry point imports `@wdio/globals`. The service's own dependencies used to bring them.

  ```sh
  npm install --save-dev @wdio/electron-service webdriverio @wdio/globals
  ```

- **pnpm with hoisting turned off, or Yarn Plug'n'Play:** these don't let a package see what it hasn't declared, so list `webdriverio`, `@wdio/types` and `@wdio/globals` as direct dependencies, even in testrunner mode.

They're optional rather than required because npm and pnpm install a missing required peer at the newest version in range, so a project even one release behind got a second copy of each package.

### App builds

#### Which app build is used

The service now finds Electron Builder apps built for Windows ARM64 and ia32 (`win-arm64-unpacked`, `win-ia32-unpacked`). It also follows Electron Builder's `defaultArch`: with `win.defaultArch: 'arm64'`, it finds the x64 build in `win-x64-unpacked`.

When your output directory holds builds for more than one architecture, the service now launches the one built for the machine running the tests, so your tests may launch a different app:

| Machine running the tests | Builds in the output directory            | v10 launched                        | v11 launches         |
| ------------------------- | ----------------------------------------- | ----------------------------------- | -------------------- |
| Windows ARM64             | `win-unpacked`, `win-arm64-unpacked`      | `win-unpacked`                      | `win-arm64-unpacked` |
| Linux x64                 | `linux-unpacked`, `linux-arm64-unpacked`  | `linux-arm64-unpacked`              | `linux-unpacked`     |
| Linux x64                 | `linux-unpacked`, `linux-armv7l-unpacked` | `linux-armv7l-unpacked`             | `linux-unpacked`     |
| Intel Mac                 | `mac`, `mac-arm64`                        | `mac-arm64`                         | `mac`                |
| Intel Mac                 | `mac`, `mac-universal`                    | `mac-universal`                     | `mac`                |
| Intel Mac                 | `mac-arm64`, `mac-universal`              | `mac-arm64`                         | `mac-universal`      |
| Apple Silicon Mac         | Forge `darwin-x64`, `darwin-arm64`        | `darwin-x64`                        | `darwin-arm64`       |
| Linux ARM64               | Forge `linux-x64`, `linux-arm64`          | `linux-x64`                         | `linux-arm64`        |
| Windows ARM64             | Forge `win32-x64`, `win32-arm64`          | `win32-x64`                         | `win32-arm64`        |
| Windows x64               | Forge `win32-ia32`, `win32-x64`           | `win32-ia32` (Electron 43 or older) | `win32-x64`          |

A machine running an x64 Node.js counts as x64, including an Apple Silicon Mac under Rosetta and a Windows ARM64 machine under emulation.

v11 also finds Electron Forge builds that v10 missed. v10 looked only for x64 builds when `browserVersion` held a Chromium version or the Electron version was unknown, and from Electron 44 it skipped `win32-ia32` and `linux-armv7l`.

If none of the builds can run on the machine, such as an Intel Mac with only `mac-arm64`, the service still launches the first one it finds, as v10 did, and now logs a warning that names the build and the machine's architecture.

To keep launching a specific build, set [`appBinaryPath`](../configuration.md#appbinarypath). See [Which build is used](../configuration.md#which-build-is-used) for the full order.

#### `getBinaryPath()` takes no Electron version

If you call the exported `getBinaryPath()`, drop the Electron version argument.

**Before (v10):**

```ts
const result = await getBinaryPath(packageJsonPath, appBuildInfo, electronVersion);
```

**After (v11):**

```ts
const result = await getBinaryPath(packageJsonPath, appBuildInfo);
```

### Mocking

#### Removed `mock()` and `isMockFunction()` overloads

Two deprecated overloads are gone from the types. Neither ever worked at runtime.

- **`mock(apiName, funcName, returnValue)`:** the service never read the third argument, so the mock had no return value. Set it with the chained setter.

  **Before (v10):**

  ```ts
  const mockGetName = await browser.electron.mock('app', 'getName', 'Mocked App');
  ```

  **After (v11):**

  ```ts
  const mockGetName = await browser.electron.mock('app', 'getName');
  await mockGetName.mockReturnValue('Mocked App');
  ```

- **`isMockFunction(name: string)`:** it always returned `false`, because Electron mocks are identified by the mock object, not looked up by name. Pass the mock itself. A string is now typed as the general `unknown` form and still returns `false`.

  **Before (v10):**

  ```ts
  expect(browser.electron.isMockFunction('app.getName')).toBe(false);
  ```

  **After (v11):**

  ```ts
  const mockGetName = await browser.electron.mock('app', 'getName');
  expect(browser.electron.isMockFunction(mockGetName)).toBe(true);
  ```

#### Bulk mock operations report every failure

A failed bulk mock operation now attempts every mock, then throws one error listing every failure. Before, it stopped at the first failure and skipped the rest.

- In `beforeTest` (`clearMocks`, `resetMocks`, `restoreMocks`), WebdriverIO reports the error as a `BeforeTest` hook failure and still runs the test.
- `clearAllMocks()`, `resetAllMocks()` and `restoreAllMocks()` reject, so they fail the test that calls them.
- The `apiName` filter on these three matches a literal prefix, so a `.` in it is no longer a regex wildcard.

#### `undefined` arguments in call data

A mock's recorded calls keep `undefined` arguments, nested ones included, where they used to become `null`. An assertion that matched an `undefined` argument with `null` now needs `undefined` there.

**Before (v10):**

```ts
expect(mockOpenExternal).toHaveBeenCalledWith(url, null);
```

**After (v11):**

```ts
expect(mockOpenExternal).toHaveBeenCalledWith(url, undefined);
```

Object properties set to `undefined` now come back too, where they used to be dropped. `toEqual` and `toHaveBeenCalledWith` ignore them, but `toStrictEqual` on `mock.calls`, `mock.lastCall` or `mock.results` now sees them.

#### `withImplementation()`

- A [`withImplementation()`](../api-reference.md#withimplementation) callback that returns a promise keeps the temporary implementation until the promise settles. It used to be restored as soon as the callback returned, so a mock call after the callback's first `await` got the original implementation.
- The callback takes only the `electron` object. Remove any extra parameters.
- `execute()` and `withImplementation()` resolve to the callback's awaited return type, so a callback that returns a promise is no longer typed `Promise<Promise<T>>`. Remove any casts or double `await`s that worked around it.
- `withImplementation()` now rejects when the callback throws, or when the function is no longer mocked. It used to resolve in both cases.

#### Browser mode: `mock(channel)` resets an existing mock

In browser mode, `browser.electron.mock(channel)` on a channel that's already mocked now resets the mock, as native mode does. It used to return the mock with its calls and implementation. After a navigation, the mock doesn't keep its implementation either.

A suite that sets an implementation in `beforeAll` and calls `mock()` again in `beforeEach` loses it. Set the implementation in `beforeEach`, or keep the mock from `beforeAll` and call `mockClear()` instead. See [`mock(channel)` Resets an Existing Mock](../browser-mode.md#mockchannel-resets-an-existing-mock).

**Before (v10):**

```ts
let mockGetUser: ElectronFunctionMock;

before(async () => {
  mockGetUser = await browser.electron.mock('get-user-data');
  await mockGetUser.mockResolvedValue({ id: 1, name: 'Alice' });
});

beforeEach(async () => {
  mockGetUser = await browser.electron.mock('get-user-data');
});
```

**After (v11):**

```ts
let mockGetUser: ElectronFunctionMock;

beforeEach(async () => {
  mockGetUser = await browser.electron.mock('get-user-data');
  await mockGetUser.mockResolvedValue({ id: 1, name: 'Alice' });
});
```

### Configuration and options

#### `devServer` is a service-level option

`devServer` is now a service-level option only, and no longer type-checks in `wdio:electronServiceOptions`. The service already ignored it there. Move it into the service options, or in standalone mode into `startWdioSession()`'s second argument. With a command or object `devServer`, set `devServerUrl` in the service options too: it's the URL the service waits for. See [Auto-managing the dev server](../browser-mode.md#auto-managing-the-dev-server).

**Before (v10):**

```ts
export const config = {
  services: ['electron'],
  capabilities: [
    {
      browserName: 'electron',
      'wdio:electronServiceOptions': {
        mode: 'browser',
        devServer: 'pnpm dev',
        devServerUrl: 'http://localhost:5173',
      },
    },
  ],
};
```

**After (v11):**

```ts
export const config = {
  services: [
    [
      'electron',
      {
        mode: 'browser',
        devServer: 'pnpm dev',
        devServerUrl: 'http://localhost:5173',
      },
    ],
  ],
  capabilities: [{ browserName: 'electron' }],
};
```

#### CDP bridge connection errors

When the `EnableNodeCliInspectArguments` fuse is enabled but the CDP bridge can't connect to the app's main process, the service now logs the connection error at error level when the session starts. Every `browser.electron` call that needs the bridge then throws `CDP bridge could not connect to the main process, API is disabled: <error>`, with the original error as its `cause`. It used to throw `CDP bridge is not available, API is disabled` and blame the fuse.

The session still starts, and tests that don't use those APIs still run. If a test or tool matches the old message, match the new one. A disabled fuse still throws the old message. See [CDP bridge could not connect to the main process](../common-issues.md#cdp-bridge-could-not-connect-to-the-main-process).

### Multiremote

#### Mocks per instance

- Each instance's `browser.electron.mock()`, `mockAll()` and class mocks only mock that instance's app, and each instance gets its own mock of a function. Before, a mock created on one instance mocked the function in every app, and a second instance's `mock()` returned and reset the first one's.
- `clearAllMocks()`, `resetAllMocks()` and `restoreAllMocks()` on an instance only touch its own mocks. On the root they cover every instance.
- `clearMocks`, `resetMocks` and `restoreMocks` set in an instance's `wdio:electronServiceOptions` apply to that instance's mocks, where they were ignored. An instance that doesn't set one uses the service-level value.

A test that relied on one instance's mock reaching another app now needs to create the mock on that instance, or on the root. See [Mocking in Multiremote](../electron-apis.md#mocking-in-multiremote).

#### Instance options take effect

Other options in an instance's `wdio:electronServiceOptions` take effect too, where they were ignored. Remove any you don't want applied.

- An instance's `mode: 'browser'` runs browser mode, and `mode: 'native'` on every instance overrides a service-level `'browser'`.
- Service-level `captureMainProcessLogs` and `captureRendererLogs` capture every instance's logs, and an instance's log options merge with the service-level ones instead of replacing them. See [Multiremote Support](../configuration.md#multiremote-support).
- Each instance's `triggerDeeplink()` uses its own `appBinaryPath` and user data directory. The root's `triggerDeeplink()` triggers the deeplink once for each instance, and its error names the instance that failed.

#### `triggerDeeplink()` on macOS

On macOS, in a multiremote session where two instances run the same app binary, `triggerDeeplink()` throws on every instance and on the root, because `open` can't pick an instance. It used to resolve, and the URL reached whichever copy of the app macOS chose. In script mode (`appEntryPoint`), every instance runs Electron itself, so it always throws. Test deeplinks on macOS without multiremote. Windows and Linux are unchanged. See [Deeplink Testing: Multiremote](../deeplink-testing.md#multiremote).

### Standalone mode

#### Concurrent sessions with a command `devServer`

In browser mode, another session in the same process can't use a command-form `devServer` at the same URL until the first session's `cleanupWdioSession()` stops it. It used to share the first session's server, which then stopped under it. To share a server between concurrent sessions, start it yourself and pass `devServerUrl` without `devServer`, or run the sessions in separate processes.

### Linux display

On WebdriverIO v10, the testrunner starts a display server itself, Weston if it's installed and Xvfb otherwise, so no `xvfb-run` wrapper is needed. The service is tested on both and needs no setting. An app with X11-only dependencies sets WebdriverIO's `displayServer: 'xvfb'`. Local runs on a Linux desktop now show the app instead of a hidden Xvfb. See [Headless & Display Servers](https://webdriver.io/docs/headless-and-display-servers).

## Verification

After updating, verify your migration:

1. **Check your versions:** `webdriverio` and the `@wdio/*` packages are 9.33.0+ or 10.2.0+, and Node.js is 22.23.4+, 24.22.1+ or 26.12.1+.
2. **Run the type checker:** it flags the removed `mock()` and `isMockFunction()` forms, extra `withImplementation()` callback parameters, and a `devServer` left in `wdio:electronServiceOptions`.
3. **Check which app launches:** without `appBinaryPath`, the launcher logs `Detected app binary at <path>`. Set `appBinaryPath` if it isn't the build you want.
4. **Run your tests:** fix assertions that expected `null` for an `undefined` argument, and multiremote tests that expected a mock on one instance to reach another app.

If you encounter issues, check the [Common Issues](../common-issues.md) documentation.
